# API Conventions

Cross-cutting conventions for every module that exposes an HTTP API. Per-module
`interfaces/README.md` files link here instead of restating these; a module's own
`interfaces/<operation>.md` files should only describe what's specific to that operation. See
ADR-0005 for why this file and the per-operation structure exist.

## Generated OpenAPI document

Every module with an HTTP API enables ASP.NET Core's built-in OpenAPI generation
(`builder.Services.AddOpenApi()` + `app.MapOpenApi()`, Development-only) rather than
hand-maintaining a schema. It's regenerated from the actual endpoint definitions on every
build/run, so it's the structural source of truth for request/response *shape* — it cannot
drift from the code the way a hand-written doc can. It does **not** replace the per-operation
`.md` files: the generated doc only knows shape (property names/types), not business meaning,
auth requirements in plain language, or which requirement/rule an endpoint implements — that
context stays in the `.md` files, which should link to the live document rather than
re-transcribing its fields.

- Dev URL pattern: `{base URL}/openapi/v1.json` (e.g. `latteAPI`:
  `http://localhost:5019/openapi/v1.json`).

## JSON conventions

ASP.NET Core Minimal API defaults, used as-is (no custom naming policy beyond one converter):

- Property names: camelCase (`createdAt`, not `CreatedAt`).
- Enums: serialize as their string name (e.g. `"Medium"`), not the underlying integer —
  requires `JsonStringEnumConverter` registered via `ConfigureHttpJsonOptions`; a module that
  skips this registration is not following convention.
- Dates/times: ISO 8601 (`DateTimeOffset`'s default `System.Text.Json` representation).

## Auth header

`Authorization: Bearer <token>` on every request to an endpoint whose `interfaces/<op>.md` says
auth is required. No custom header scheme.

## Error response bodies

Status codes are documented per-operation; the body shape is standardized here so a client
only needs to learn it once:

| Status | Body | Notes |
|---|---|---|
| `400 Bad Request` | `{ "error": "<message>" }` | `message` is a human-readable description, not a machine-parseable code — don't pattern-match on its text. |
| `401 Unauthorized` | empty | On a token-protected endpoint (`RequireAuthorization()`), framework-generated by JWT Bearer middleware and includes a `WWW-Authenticate: Bearer` response header. On an anonymous endpoint whose own logic rejects the request (e.g. bad login credentials via `Results.Unauthorized()`), there is no middleware challenge and therefore no `WWW-Authenticate` header — see that operation's own file for its exact sample. |
| `404 Not Found` | empty | `Results.NotFound()` — no body. |

This is the *current* actual behavior (verified against `latteAPI` 2026-08-22), documented here
deliberately because two independent from-docs reconstructions of `latteAPI` disagreed on the
`400` shape before this file existed — see ADR-0005's context. If a future change introduces a
structured error body for `401`/`404` (e.g. RFC 9457 Problem Details), update this table as part
of that change, not after.

## Health check payload

`GET /health` (or equivalent) returns `200 OK` with `{ "status": "ok" }` when healthy. A module
whose health check also verifies an upstream dependency (e.g. `latteMCP` verifying `latteAPI`,
see ADR-0004) documents its specific non-2xx failure behavior in its own
`interfaces/get-health.md` — this file only fixes the shared success-shape convention.
